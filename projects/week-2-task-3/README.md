# GOOST CHAT — день 8: токены и контекст

Обычный чат с облачной моделью DeepSeek. Слева — список диалогов, справа — переписка и поле сообщения. Каждый чат сохраняет свой контекст в SQLite и восстанавливает его после перезапуска сервера.

Основа — `week-2-task-2`. Новый день показывает токены запроса, истории и ответа, рост стоимости и отказ при переполнении учебного окна. История, метрики завершённых ходов и результаты повторных запросов сохраняются в SQLite.

## Запуск

Нужен Python 3.11+ и ключ DeepSeek. Сторонних библиотек, сборщика и CDN нет.

В `.env` в корне репозитория:

```env
DEEPSEEK_API_KEY=your_api_key
```

Из корня репозитория:

```powershell
python projects/week-2-task-3/web.py --port 8765
```

Открой [http://127.0.0.1:8765](http://127.0.0.1:8765). При запуске без `--port` используется порт `8000`. Остановить сервер — `Ctrl + C`. После изменений Python-кода перезапусти сервер; после изменений интерфейса обнови страницу.

## Как пользоваться

- При первом открытии создаётся пустой чат. «Новый чат» добавляет отдельный диалог и сохраняет прежние.
- Выбирай чаты слева. Название автоматически берётся из первого сообщения; кнопка «⋯» позволяет переименовать или удалить чат. Удаление требует подтверждения и необратимо.
- Отправляй сообщения кнопкой со стрелкой или `Enter`. `Shift + Enter` переносит строку; `Ctrl / Cmd + Enter` тоже отправляет.
- Во время ответа можно переключаться между чатами и писать черновики. Ответ остаётся в том чате, откуда отправлен запрос.
- Черновики отдельные для каждого чата, но хранятся только в памяти текущей страницы. Переключение чатов их сохраняет; обновление страницы — нет.
- Кнопка «Скопировать» копирует ответ. Текст модели показывается как обычный текст: HTML и Markdown не исполняются.
- В заголовке есть кнопка обновления чатов и проверки связи. Она полезна после потери соединения или работы во второй вкладке.
- На узком экране список чатов открывается кнопкой слева в заголовке. Закрытие — выбор чата, Escape, кнопка закрытия или нажатие вне панели.

В одном браузерном профиле одновременно выполняется одна операция изменения данных. Пока модель отвечает, создание, переименование, удаление и новая отправка заблокированы; чтение других чатов доступно.

При сетевой ошибке текст сохраняется. Клиент сначала читает историю, затем проверяет исходную отправку с тем же `request_id`: уже выполненный запрос не создаёт второй ответ. Если сервер был остановлен во время запроса и исход неизвестен, интерфейс сообщает об этом. Повторная отправка с новым идентификатором выполняется только по действию пользователя — сначала проверь историю.

## Интерфейс

Основной фон — Dark Mode 900 `#161C29`, поверхности используют градации Dark Mode, текст — Neutral, акцент — Primary 500 `#FCBF40`. Полные шкалы Dark Mode, Neutral, Primary, Secondary, Success, Warning и Error переведены в OKLCH и собраны в `static/tokens.css`; интерфейс подключает их через семантические алиасы.

Типографика — локально подключённый TT Wellingtons с проверенной кириллицей в начертаниях Regular, DemiBold и Bold. WOFF2-файлы отдаются тем же сервером, поэтому шрифт работает и при открытии интерфейса с другого устройства. Segoe UI остаётся системным fallback. Интерфейс поддерживает клавиатуру, видимый фокус, native dialog и уменьшение анимации через настройки системы.

## Хранение и восстановление

База: `projects/week-2-task-3/data/context.sqlite3`. Папка `data/` исключена из Git. Данные вчерашнего проекта не копируются.

- `chats` хранит владельца, название, историю сообщений, токены, даты и JSON-массив `turn_metrics`.
- `requests` хранит идентификаторы отправок и их результаты для безопасного повтора.
- Запрос пользователя, ответ модели, метрики и снимок результата для `request_id` записываются одной транзакцией после успешного API-вызова. Ошибочный ответ не дописывает половину диалога. Если запись снимка не удалась, откатываются также история и метрики; запрос остаётся `pending`, повтор не вызывает провайдера снова.
- Чаты не удаляются по таймеру бездействия.
- При запуске схемы версий 0 и 1 мигрируют в версию 2. Старые записи из `conversations` переносятся; исходная таблица остаётся в базе. Старые cookie `chat_session` и `pitch_session` распознаются и заменяются на `goost_owner`. Исторические `total_tokens` сохраняются, а отсутствующие метрики старых ходов не выдумываются: массив изначально пуст. Повторный запуск миграцию не дублирует. Повреждённые метрики вызывают явную ошибку чтения.
- Системный промпт создаётся агентом отдельно; в пользовательской истории хранятся только сообщения пользователя и ассистента.

Проверка задания:

1. Напиши: «Запомни: мой проект называется GOOST, релиз в пятницу».
2. Создай другой чат и обсуди другую тему.
3. Вернись в первый чат, останови и снова запусти сервер.
4. Обнови страницу в том же браузере. История и список чатов восстановятся.
5. Спроси: «Как называется мой проект и когда релиз?». Модель получит сохранённый контекст первого чата.

## Браузер и безопасность

Доступ к чатам связан с непрозрачной HttpOnly-cookie `goost_owner`, срок — один год. Это идентификатор браузера, а не вход в аккаунт. Другой профиль, устройство, домен или очистка cookie означают другой набор чатов. Сами старые данные остаются в SQLite, но без cookie интерфейс не сможет связать их с этим браузером.

Сервер слушает только `127.0.0.1`, проверяет Host и Origin, использует SameSite=Strict и ограничивает тело запроса. Все операции с чатами проверяют владельца. API-ключ остаётся в Python-процессе и не передаётся браузеру. Переписка отправляется облачному DeepSeek API; локальная база не зашифрована.

Для временного показа с телефона можно использовать уже установленный Cloudflare Tunnel:

```powershell
cloudflared tunnel --url http://127.0.0.1:8765
```

После получения HTTPS-адреса запусти сервер с этим точным origin:

```powershell
python projects/week-2-task-3/web.py --port 8765 --public-origin https://your-tunnel.trycloudflare.com
```

Замени пример на фактический адрес туннеля. Для него cookie получает флаг Secure. Локальный адрес и адрес туннеля имеют разные cookie и наборы чатов.

Туннель публичный и не добавляет авторизацию: получивший ссылку может делать запросы за счёт твоего API-ключа. Не публикуй адрес и останови туннель после демонстрации. Для постоянной публикации потребуется настоящая авторизация и ограничение расходов. Сервер рассчитан на один локальный процесс.

## API

Все ответы — JSON. Ошибка имеет вид `{"error": {"code": "...", "message": "..."}}`.

| Метод и путь | Тело | Результат |
| --- | --- | --- |
| `GET /api/chats` | — | `chats`, `model`, `busy` |
| `POST /api/chats` | `{}` | `201`, `chat` |
| `GET /api/chats/{id}` | — | `chat` с сообщениями |
| `PATCH /api/chats/{id}` | `{"title": "Новое название"}` | `chat` |
| `DELETE /api/chats/{id}` | — | `{"deleted": "id"}` |
| `POST /api/chats/{id}/messages` | `{"message": "Привет", "request_id": "UUID"}` | `chat` с ответом |
| `POST /api/chats/{id}/token-preview` | `{"message": "Привет"}` | `estimate`, без API-вызова и записи в БД |

Чат содержит `id`, `title`, `created_at`, `updated_at`, `message_count`, `total_tokens`; подробный ответ дополнительно содержит `messages`, `model`, `busy`, `context`, `config`, `turn_metrics`. Даты — Unix timestamp в секундах. Текст сообщения — до 4000 символов; название — от 1 до 100. Повторяй одну логическую отправку только с тем же `request_id` и тем же текстом.

Preview допускает пустой текст, проверяет владельца, Origin, размер и точный набор ключей. Лимит HTTP-тела остаётся 32 KiB. Во время API-запроса preview доступен и оценивает последний сохранённый контекст.

`context` и `estimate` содержат `system_tokens`, `history_tokens`, `request_tokens`, `message_overhead_tokens`, `prompt_tokens`, `reserved_output_tokens`, `required_tokens`, `context_limit`, `remaining_tokens`, `overflow`, `estimator`. В подробном чате `context` рассчитан для пустого черновика. `config` содержит `context_limit` и `max_tokens`.

Каждый элемент `turn_metrics`: `turn_index` (номер пары сообщений, начиная с 1), оценки `request_tokens`, `history_tokens`, `system_tokens`, `prompt_tokens`, `answer_tokens`, объект `provider_usage` и `cost`. Индексы старых ходов после миграции могут отсутствовать.

Переполнение возвращает HTTP 422: `{"error":{"code":"context_limit","message":"…","estimate":{…}}}`. Проверка выполняется до вызова DeepSeek и резервирования `request_id`; история и метрики не меняются. Завершённый повтор проверяется раньше лимита и возвращает сохранённый снимок даже после роста истории. Другие ошибки провайдера возвращают безопасное сообщение HTTP 502 без деталей upstream.

## Что именно считаем

- Локальная оценка текста: `ceil(len(text.encode("utf-8")) / 4)`. Оценка сообщения считается отдельно; добавляются 4 служебных токена на сообщение и 3 на подготовку ответа. Это воспроизводимая эвристика `utf8_bytes_div4_v1`, а не официальный tokenizer DeepSeek. Кириллица и emoji занимают больше UTF-8-байтов; оценка может отличаться от фактического usage.
- `prompt_tokens` оценки = системный промпт + вся история + текущий запрос + служебные токены. `required_tokens` дополнительно включает резерв ответа `max_tokens=250`.
- Учебное окно приложения — 2048 токенов. Равенство разрешено; отказ происходит только при `required_tokens > context_limit`. Это лимит данного приложения, не максимальное окно DeepSeek. История автоматически не обрезается и не суммаризируется.
- `answer_tokens` — локальная оценка видимого ответа. `provider_usage` — реальные значения, полученные от API: `prompt_tokens`, `completion_tokens`, `total_tokens`, `prompt_cache_hit_tokens`, `prompt_cache_miss_tokens`. Отсутствующее значение — `null`, не ноль. При ответе с одним `total_tokens` остальные поля остаются неизвестными. Отрицательные, дробные, булевы и противоречивые счётчики отклоняются до сохранения хода.
- `total_tokens` чата сохраняет прежний смысл: сумма известных `usage.total_tokens` успешных API-вызовов. Это не размер текущей истории: предыдущая история снова входит во входящие токены каждого нового запроса. При неизвестном usage сумма не увеличивается; она неполна, что видно по метрикам ходов.

## Стоимость

`cost` — диапазон расчётной стоимости хода в USD, не счёт провайдера. Рассчитывается только для `deepseek-v4-flash`, когда известны cache hit, cache miss и completion. При недостаточном usage — `null`. `min_usd` и `max_usd` передаются десятичными строками; расчёт через Python `Decimal`.

Тарифы проверены 2026-09-09 по [официальной странице DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/): за 1 млн токенов cache hit $0.007–0.014, cache miss $0.22–0.44, output $0.66–1.32. Диапазон учитывает off-peak/peak; приложение не определяет момент фактического биллинга. Каждый результат хранит `currency`, `pricing_date`, `source`; сохранённые оценки после изменения тарифов не пересчитываются. Сумма доступных оценок неполна, если у отдельных ходов нет `cost`.

## Три сценария дня

1. Новый чат → «Короткий запрос» → отправка. Сравни оценку запроса и полученный usage; смотри оценку ответа.
2. «Длинный запрос» → отправка. Повтори несколько ходов в том же чате: растут история и входящий контекст, модель повторно обрабатывает сохранённую переписку. Фактическая стоимость зависит также от длины ответа и попадания в cache, поэтому не обязана расти строго на каждом ходе.
3. Новый чат → «Переполнение» (3847 символов кириллицы) → проверка/отправка. Локальная оценка вместе с системой и резервом превышает 2048: HTTP 422, провайдер не вызывается, история и метрики остаются прежними. Можно сократить текст или создать новый чат. Если уже заполнена сама история, поможет новый чат.

## CLI и параметры модели

Консольный режим тоже сохраняет историю, но использует отдельный диалог `cli`:

```powershell
python projects/week-2-task-3/main.py
```

Пиши любой вопрос; `exit` завершает работу. Параметры в `AgentConfig` файла `main.py`:

```python
model: str = "deepseek-v4-flash"
temperature: float = 0.5
top_p: float = 1.0
max_tokens: int = 250
timeout: int = 60
context_limit: int = 2048
```

`max_tokens` ограничивает длину ответа и резервирует место в контексте. Оба токен-лимита должны быть положительными целыми числами, `max_tokens < context_limit`. Изменение резерва меняет допустимый размер входа. CLI выводит метрики после ответа и явный отказ при переполнении.

## Проверки

```powershell
python -m unittest discover projects/week-2-task-3
node --check projects/week-2-task-3/static/app.js
```

Тесты backend проверяют границы ниже/ровно/выше лимита, отсутствие сетевых и дисковых изменений при переполнении, полный/отсутствующий/частичный/некорректный usage, Decimal-стоимость, версии БД 0/1/2, восстановление метрик, атомарный откат, повтор без двойного начисления, preview и изоляцию. Тестовые ответы подменяются локально и не расходуют API-токены. Отдельная интеграционная проверка нужна для живого DeepSeek usage, расхождения с эвристикой и браузерных сценариев на desktop/mobile.
