# GOOST CHAT — день 9: сжатие контекста

Цель задания — заменить старую часть диалога кратким summary, оставить последние сообщения и сравнить расход токенов и сохранение фактов. Основа — проект дня 8, `week-2-task-3`: Python-сервер, облачный DeepSeek API, SQLite и браузерный интерфейс GOOST.

## Запуск

Нужен Python 3.11+. Сторонних Python-библиотек, сборки frontend и CDN нет. Добавь ключ в `.env` в корне репозитория:

```env
DEEPSEEK_API_KEY=your_api_key
```

Из корня репозитория:

```powershell
python projects/week-2-task-4/web.py --port 8765
```

Открой [http://127.0.0.1:8765](http://127.0.0.1:8765). Без `--port` сервер использует `8000`; остановка — `Ctrl + C`. Если порт занят другим учебным проектом, выбери свободный порт.

Данные этого дня: `projects/week-2-task-4/data/context.sqlite3`. История других проектов автоматически не переносится. Папка `data/` исключена из Git.

## Как работает сжатие

Полная переписка хранится в `chats.messages` и остаётся доступной в интерфейсе. Отдельное поле `chats.compression` содержит режим, summary, число уже обработанных сообщений и метрики вызовов суммаризации.

- `full`: модель получает всю историю. Сохранённый summary не удаляется и не обновляется.
- `compressed`: перед следующим ответом старая часть истории сжимается, а последние **6 сообщений** остаются дословно. Сообщением считается отдельная реплика пользователя или ассистента, поэтому 6 сообщений — 3 завершённых хода.
- Один вызов суммаризации обрабатывает **не более 10 новых старых сообщений**. Вход каждого вызова — предыдущий summary плюс очередная порция. Если после работы в `full` накопилась длинная история, сервер обрабатывает весь backlog последовательными порциями.
- После завершения ответа в истории появляются ещё 2 сообщения. Их старшую часть сервер обработает перед следующей отправкой; поэтому после ответа интерфейс может снова показывать ожидающее сжатие.

Summary передаётся отвечающей модели как справочные данные в сообщении `user`, с отдельным системным указанием считать эти данные недоверенными. Исходные пользовательские сообщения не становятся системными инструкциями. Суммаризатор получает JSON с `previous_summary` и `new_messages`.

В интерфейсе можно переключать режим текущего чата, смотреть summary, число обработанных и ожидающих сообщений, сравнение входящего контекста и расход на суммаризацию. Переключение режима само по себе не вызывает модель.

## Что измеряется

`comparison` считает оба варианта независимо от выбранного режима:

- `full_prompt_tokens` — оценка входа со всей историей;
- `compressed_prompt_tokens` — оценка входа с уже сохранённым summary и ещё не обработанными сообщениями;
- `saved_tokens = full_prompt_tokens - compressed_prompt_tokens` — разница со знаком. Отрицательное значение означает, что summary с обрамлением пока длиннее исходной части.

Это локальная эвристика `ceil(UTF-8 bytes / 4)` со служебными накладными расходами, а не официальный токенизатор. Preview не создаёт будущий summary: при `pending_compression: true` фактический вход после суммаризации изменится. Пока summary нет, два варианта могут совпадать.

`turn_metrics` и `total_tokens` относятся к основным ответам чата. Отдельно в `compression`:

- `summary_metrics` — метрики каждого завершённого вызова суммаризации, включая `provider_usage` и `cost`;
- `summary_api_tokens` — сумма фактических `total_tokens` суммаризации; `null`, если хотя бы один вызов не вернул этот счётчик;
- `summary_cost` — сумма диапазонов `min_usd` / `max_usd`; `null`, если стоимость хотя бы одного вызова неизвестна.

Стоимость оценивается через `Decimal` по зафиксированным в коде тарифам и дате `2026-09-09`. Это оценка, а не счёт провайдера. Выигрыш входящих токенов не равен денежной экономии: нужно учитывать дополнительные вызовы суммаризации, длину ответов и кеш провайдера. Метрики записываются только вместе с успешным ходом; оплаченные вызовы перед ошибкой следующего API-вызова или записи в БД в сохранённые итоги не входят.

## Ограничения и надёжность

Основной чат использует учебное окно **2048** токенов с резервом **250** на ответ. Суммаризатор имеет отдельный локальный бюджет **32768** и резерв **500**. Эти значения не описывают максимальное окно модели у провайдера. В промпте суммаризации указано до 150 слов; жёсткая проверка ответа — не более 4000 символов.

Сжатие не гарантирует, что длинное сообщение или последние 6 реплик поместятся в окно. Переполнение возвращает `422 context_limit`. Если переполнение очевидно до суммаризации, API не вызывается. Если лимит превышен после неё или в её отдельном бюджете, чат остаётся прежним, но уже выполненные облачные вызовы могли быть оплачены.

До первого облачного вызова сервер резервирует `request_id`. История, summary, метрики и снимок ответа записываются одной SQLite-транзакцией. Ошибка суммаризации, основного ответа или записи снимка не оставляет частично изменённый диалог. Повтор завершённого `request_id` возвращает сохранённый снимок без новых вызовов API, даже после смены режима и перезапуска. Состояние `pending` означает неизвестный исход: повтор не вызывает модель автоматически. Перед новой отправкой проверь историю.

SQLite использует схему v3; старые схемы мигрируют, отсутствующие метрики не выдумываются. Повреждённые состояния отклоняются при чтении. Удаление чата удаляет его историю, summary и связанные request-снимки.

Сервер рассчитан на один локальный процесс. Непрозрачная HttpOnly-cookie связывает чаты с браузерным профилем; это не пользовательский аккаунт. Проверяются владелец, Host, Origin, JSON и размеры запросов. API-ключ остаётся на сервере. Текст модели отображается без исполнения HTML. Переписка и summary отправляются DeepSeek; локальная SQLite не зашифрована. Summary может потерять или исказить факты: качество нужно проверять на конкретных диалогах.

При показе через туннель нужен точный HTTPS-origin:

```powershell
python projects/week-2-task-4/web.py --port 8765 --public-origin https://your-tunnel.trycloudflare.com
```

Туннель не добавляет авторизацию: владелец ссылки сможет расходовать серверный API-ключ. Адрес туннеля и localhost используют разные cookie.

## API

Все тела и ответы — JSON; изменяющие запросы требуют `Content-Type: application/json`. Ошибка: `{"error":{"code":"...","message":"..."}}`.

| Метод и путь | Тело | Результат |
| --- | --- | --- |
| `GET /api/chats` | — | `chats`, `model`, `busy` |
| `POST /api/chats` | `{}` | `201`, `chat` |
| `GET /api/chats/{id}` | — | Подробный `chat` |
| `PATCH /api/chats/{id}` | `{"title":"Название"}` | `chat` |
| `DELETE /api/chats/{id}` | — | `deleted` |
| `POST /api/chats/{id}/messages` | `{"message":"Привет","request_id":"request_001"}` | `chat` с ответом |
| `POST /api/chats/{id}/compression` | `{"mode":"full"}` или `{"mode":"compressed"}` | `chat` после смены режима |
| `POST /api/chats/{id}/token-preview` | `{"message":"Черновик"}` | `estimate`, `comparison`; без записи и API |

Подробный `chat` включает `messages`, `turn_metrics`, `total_tokens`, `compression`, `comparison`, `context`, `config`, `model`, `busy` и метаданные чата. `compression` содержит `mode`, `summary`, `summarized_count`, `summary_metrics`, `summary_api_tokens`, `summary_cost`, `keep_last_messages`, `pending_messages`.

`context` и preview `estimate` содержат оценки запроса/истории/системы/накладных расходов, `prompt_tokens`, `required_tokens`, `reserved_output_tokens`, `context_limit`, `remaining_tokens`, `overflow`, `estimator`, `pending_compression`. В `chat.context` черновик пустой; preview учитывает переданное сообщение. HTTP-тело ограничено 32 KiB, сообщение — 4000 символами, название — 100. `request_id`: 8–128 латинских букв, цифр, `_` или `-`; одна логическая отправка повторяется с прежним идентификатором и текстом.

## Сценарий сравнения качества и токенов

1. Создай два чата. В первом выбери `full`, во втором — `compressed`.
2. Отправь в оба одинаковую первую реплику: «Проект GOOST. Релиз 18 сентября. Бюджет 40 тысяч рублей. Ответственный — Анна. Главное ограничение — без платной рекламы».
3. Сделай ещё несколько одинаковых коротких ходов о плане релиза. После четвёртого завершённого хода исходный факт окажется за пределами последних 6 сообщений; следующая отправка в `compressed` запустит суммаризацию.
4. Спроси в обоих чатах: «Назови проект, дату релиза, бюджет, ответственного и главное ограничение». Сверь 5 фактов с исходной репликой и отметь пропуски/искажения.
5. Сравни `comparison`, фактический `provider_usage` основного ответа и отдельные расходы summary. Ответы модели могут различаться, поэтому для честного вывода учитывай весь полученный диалог и повтори опыт на нескольких наборах фактов.
6. Продолжи сжатый диалог, добавь новые ограничения и снова проверь старые факты: новый summary должен учитывать предыдущий. Перезапусти сервер и убедись, что полный transcript, summary и метрики восстановились.

Это сценарий для живой проверки, а не утверждение о доказанном качестве DeepSeek. Автоматическая валидация использовала подменённые ответы провайдера и проверяла механику запросов, сохранения и UI.

## Выводы живого запуска

В двух чатах было отправлено по 12 одинаковых запросов: один работал с полной историей, второй — с summary и последними 6 сообщениями. Оба итоговых ответа сохранили название проекта GOOST, дату релиза 18 сентября, бюджет 40 тысяч рублей, ответственную Анну, запрет платной рекламы, аудиторию, канал запуска, план и поздние ограничения.

В сжатом чате к концу опыта 16 сообщений были перенесены в summary, ещё 2 ожидали следующего цикла. Оценка входящего контекста уменьшилась примерно с 1230 до 769 токенов — на 461 токен, или около 37%. При этом создание и обновление summary отдельно потребовало 2175 API-токенов. Поэтому на коротком диалоге сжатие уменьшает размер следующего запроса, но ещё не гарантирует экономию общей стоимости: выгода появляется на длинной истории, когда сохранённое summary многократно используется в следующих запросах.

В этом запуске заметной потери фактов не произошло, но это не гарантируется архитектурой. Summary — результат работы модели, поэтому оно может пропустить или исказить деталь. Практический компромисс: хранить полный transcript как источник истины, оставлять последние сообщения дословно, а summary использовать только как компактную память с отдельным учётом её стоимости.

## Проверки и параметры

Из корня репозитория:

```powershell
python -m unittest discover -s projects/week-2-task-4
node --check projects/week-2-task-4/static/app.js
```

Backend-тесты проверяют ограниченные порции backlog, передачу старого summary, сохранение последних реплик, read-only preview, отрицательную разницу, отсутствие usage, изоляцию владельцев, миграцию, rollback и replay после restart. Облачные запросы в тестах подменяются и не расходуют токены.

Основные настройки — `AgentConfig` в `main.py`: модель `deepseek-v4-flash`, `temperature=0.5`, `top_p=1.0`, `max_tokens=250`, `timeout=60`, `context_limit=2048`. Количество последних сообщений и размер порции задают `KEEP_LAST_MESSAGES=6` и `SUMMARY_BATCH_MESSAGES=10`; бюджет суммаризатора задаётся в `Handler.compress` файла `web.py`.

`python projects/week-2-task-4/main.py` запускает унаследованный CLI с полной историей. Сжатие, переключение режимов и сравнение этого задания доступны через `web.py` и его HTTP API.
