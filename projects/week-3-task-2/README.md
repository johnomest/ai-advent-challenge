# День 12: профили пользователя

Краткое саммари: профиль автоматически задаёт стиль, формат и предпочтения каждого следующего запроса.

## Запуск

Из корня репозитория:

```powershell
python projects/week-3-task-2/web.py --port 8769
```

Открыть http://127.0.0.1:8769/. Нужны Python 3.10+ и сеть для DeepSeek API. Ключ `DEEPSEEK_API_KEY` — переменная окружения либо корневой `.env`. Новых библиотек нет. Модель и лимиты — `AgentConfig` в `main.py`.

Проект самостоятельный. База создаётся в `projects/week-3-task-2/data/context.sqlite3`; каталог исключён из Git. Базы и секреты предыдущих дней не копируются. Cookie определяет владельца браузера внутри базы этого проекта: это локальная изоляция, не полноценный аккаунт.

## Видео: 2–4 минуты

1. Сказать: «Сравню одинаковый вопрос в двух чистых чатах с разными профилями».
2. Создать чат A. В «Профиль пользователя» раскрыть редактор. Заполнить: название «Кратко»; стиль «Просто и кратко»; формат «Ровно три коротких пункта»; ограничения «Без жаргона». Нажать «Создать новый профиль», выбрать его и «Применить профиль».
3. Отправить: «Объясни, как подготовить запуск музыкального сервиса». Показать выбранный профиль и ответ.
4. Создать чистый чат B. Создать и применить профиль «Подробно»: стиль «Технически подробно»; формат «План с пояснениями и примером»; ограничения «Поясняй новые термины». Отправить дословно тот же вопрос.
5. Сравнить ответы, переключая чаты. У каждого свой выбранный профиль. Отправить в B «А как проверить результат?» без повторения предпочтений.
6. Обновить страницу: выбор сохранился. Изменить стиль выбранного профиля и сохранить; следующий запрос должен получить новое значение.
7. Итог: «Профиль подставляется приложением каждый раз. История старых ответов не переписывается».

Критерий успеха: выбранные профили различаются по чатам и сохраняются после refresh; состав payload подтверждён автотестом. Точное число пунктов в живом ответе — предпочтение модели, не программная гарантия. Сравнивать свежие чаты: прежние ответы влияют на результат.

## Что реализовано

- Слои памяти: `short_term` и `working` принадлежат чату; `long_term` принадлежит владельцу и доступна всем его чатам этого проекта. Все слои сохраняются явно, только кнопкой.
- Краткосрочные записи — отдельные заметки текущего разговора. Это не копия истории и не автоматическая выжимка; история по-прежнему выбирается стратегией контекста. Новый чат не наследует локальные заметки.
- Каждому слою доступны до 12 пар строк: ключ 60 символов, значение 240, JSON до 4096 байт UTF-8. Пустой редактор очищает слой.
- Общий `build_context` используется предпросмотром и реальным запросом. Порядок: системные правила, структурированные данные приложения, выбранная история, текущая реплика. Слои передаются как данные, не как системные инструкции.
- Старые стратегии `sliding_window`, `sticky_facts`, `branching`, метрики, переименование и удаление чатов сохранены. Для основной демонстрации выбрать окно N=1: так механизм явной памяти виден отдельно от истории.
- Ветви получают префикс переписки, но новые локальные слои, профиль, FSM и инварианты начинают с начальных значений; будущая память исходного чата в checkpoint не переносится. Долговременная память остаётся общей.
- Во время ответа запрещены изменения состояния того же владельца: HTTP 409. Другие владельцы независимы. Ошибка провайдера/формата не добавляет половину хода; ответ, метрики и replay фиксируются одной транзакцией.
- Повтор `request_id` возвращает прежний снимок, даже после изменения памяти или профиля. Снимок может отличаться от актуального состояния; обновление чата загружает текущие данные.

## API

Существующие `/api/chats`, `/messages`, `/token-preview`, `/branches` сохранены. Ошибки: `{"error":{"code":"…","message":"…"}}`.

- `GET/PATCH /api/chats/:id/memory`; PATCH: `{"layer":"working","entries":{"goal":"StageFlow"}}` → `{chat}`. Разрешены `short_term`, `working`.
- `GET/PATCH /api/memory`; PATCH: `{"entries":{"name":"Алексей"}}` → `{memory}`. Это словарь долговременных фактов владельца.
- Полный chat DTO включает `memory`, `profile_id`, `profile`, `task`, `invariants`, `last_check`. Недоступные на этом дне функции — `null`.
- `POST /api/chats/:id/token-preview` с `{"message":"…"}` → `{estimate}`; `memory_counts` показывает число записей каждого слоя. API модели не вызывается.

### Профили

- `GET/POST /api/profiles`; POST: `{"name":"Кратко","style":"Просто","format":"Три пункта","constraints":"Без жаргона"}` → `{profile,profiles}`.
- `PATCH /api/profiles/:id` — целиком заменить те же четыре поля; `DELETE` — удалить профиль и снять его выбор со всех чатов владельца. Ответ содержит `profiles`.
- `PATCH /api/chats/:id` с `{"profile_id":"…"}` или `{"profile_id":null}` → `{chat}`.
- До 20 профилей на владельца; имя до 80 символов, остальные поля до 500. Чужой профиль — 404. Изменения общего профиля действуют со следующего запроса во всех использующих его чатах.


## Проверки

```powershell
Push-Location projects/week-3-task-2
python -m unittest -q
Pop-Location
```

Тесты используют временную SQLite и подставной API. Они проверяют успешный путь, ошибку/откат, owner isolation, replay, переполнение, реальный состав отправляемого payload, миграцию схемы и перезапуск. Запускайте каждый проект отдельно: имена модулей одинаковые.

Сценарий видео — ручная проверка с живым DeepSeek; автоматические ответы не доказывают качество реальной модели. Ключ, `.env` и личные чаты в запись не включать. Проверить также узкое окно: панель настроек открывается кнопкой, длинные значения остаются читаемыми.

## Границы

Сохранённая память и предпочтения доступны модели, но смысловое качество ответа зависит от неё. Оценка токенов — эвристика UTF-8; стоимость берётся из исторической таблицы проекта, не из текущего счёта провайдера. После ошибки провайдер уже мог тарифицировать запрос.

Сервер рассчитан на один локальный процесс; owner-lock хранится в памяти процесса. Не запускать несколько серверов поверх одной базы. Проверить живой API, его JSON-режим и доступность выбранной модели в используемом окружении. История и память хранятся локально в SQLite без шифрования.
