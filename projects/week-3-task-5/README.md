# День 15 — контролируемые переходы задачи

Короткое саммари: состояние задачи управляется кодом. Выполнение открывается после утверждения плана, проверка — после сохранения результата, завершение — после успешного отчёта. Запрещённый переход оставляет задачу без изменений. Модель отвечает в формате текущего этапа и не меняет состояние самостоятельно.

## Запуск

Из корня репозитория:

```powershell
python projects/week-3-task-5/web.py --port 8772
```

Открыть http://127.0.0.1:8772/. Нужны Python 3.10+ и доступ к DeepSeek для сообщений. Используется стандартная библиотека Python, дополнительных пакетов нет. Ключ `DEEPSEEK_API_KEY` берётся из переменной окружения либо корневого `.env`. Не добавляйте ключ в исходники. Без ключа доступны интерфейс, сохранение задачи и проверки переходов; отправка модели вернёт ошибку провайдера.

Проект независим от дня 14. Новая SQLite создаётся в `projects/week-3-task-5/data/context.sqlite3`, схема версии 5. Данные предыдущих дней не копируются и не мигрируют: чужая версия базы отклоняется до изменения таблиц. Каталог `data/` исключён из Git. Порт 8772 — также значение по умолчанию.

`main.py` содержит CLI обычной переписки в стадии planning; для полного управления FSM используйте Web/API. Модель, лимиты и timeout задаёт `AgentConfig`.

## Видео: точный сценарий на 3 минуты

Перед записью запустите сервер, откройте страницу и создайте новый чат. Для примера используется задача «Python CLI для списка дел». Скопируйте три коротких артефакта из шагов ниже; показывайте переходы после сохранения. Ключ, `.env` и личные чаты в запись не включать.

1. **0:00–0:20.** Показать «Состояние задачи», этап «Планирование», ревизию 0. Сказать: «День 15: порядок работы закреплён в коде. Модель предлагает ответы, переходы выполняет сервер».
2. **0:20–0:40.** В «Перейти к этапу» выбрать «Проверка», нажать «Перейти». Показать объяснение отказа и неизменные этап/ревизию. Затем выбрать «Выполнение» и нажать «Перейти»: сервер потребует сохранённый и утверждённый план. Сказать: «Нельзя перескочить этап или начать без утверждения».
3. **0:40–1:10.** В «План» вставить `1. Написать Python CLI для списка дел. 2. Проверить добавление задачи и пустой ввод.` Нажать «Сохранить план», затем «Утвердить сохранённый план». Выбрать «Выполнение» → «Перейти». Показать новый этап и доступный переход. Сказать: «Изменение плана снимает утверждение. Сначала подтверждаю сохранённую версию».
4. **1:10–1:35.** В «Результат выполнения» вставить `Готов Python CLI: добавляет задачу; пустой ввод отклоняет.` Нажать «Сохранить результат». Выбрать «Проверка» → «Перейти». Сказать: «Без результата выполнения сервер не разрешит проверку».
5. **1:35–2:00.** Выбрать результат проверки «Не пройдена», отчёт `Обнаружена ошибка обработки пробелов.` Нажать «Сохранить проверку». Выбрать «Завершено» → «Перейти»: показать отказ. Выбрать «Выполнение» → «Перейти»: показать очищенные результат и проверку. Сказать: «Неуспешная проверка запрещает завершение. Возврат удаляет устаревшие артефакты».
6. **2:00–2:25.** Нажать «Пауза», обновить страницу. Показать сохранённые этап, план, ревизию, недоступную отправку и заблокированные редакторы задачи. Нажать «Продолжить». Сказать: «Пауза переживает перезагрузку. Продолжаю с того же этапа».
7. **2:25–2:50.** Сохранить результат `Обработка пробелов исправлена.` Перейти к «Проверка». Выбрать «Пройдена», сохранить отчёт `Добавление, пустая строка и пробелы проверены.` Перейти к «Завершено». Открыть «История изменений», показать последовательность переходов. Сказать: «Завершение возможно только после успешной проверки. Дальнейшие переходы закрыты».
8. **2:50–3:00.** Итог: «FSM, ревизии и проверки реализованы в приложении. Тип ответа модели проверяется; смысл свободного текста всё ещё требует человеческой оценки».

Дополнительная проверка модели вне трёхминутной записи: в новом чате отправить `Составь план Python CLI для списка дел. Не начинай реализацию.` На planning сервер принимает только `kind=plan`. Попытки ответить `implementation` или изменить `stage` воспроизводимо проверяются автотестами. Живая модель может следовать инструкции, поэтому уговаривание нарушить её не заменяет тест ошибочного ответа.

## Состояние и граница исполнения

Путь изменения: `PATCH /api/chats/:id/task` → `ContextStore.apply_task_action` → `BEGIN IMMEDIATE` → чтение задачи по владельцу и ID → проверка схемы, ревизии и условий → одна запись задачи с новой ревизией и историей → commit. Отказ не меняет этап, артефакты, ревизию, историю или `updated_at`.

Единственная таблица переходов `TRANSITIONS` в `main.py`:

```text
planning   -> execution
execution  -> validation
validation -> execution | done
done       -> нет переходов
```

Условия: planning → execution требует непустой сохранённый и утверждённый план; execution → validation требует непустой результат; validation → done требует `passed` с непустым отчётом. Возврат validation → execution очищает `execution_result` и `validation`, сохраняя утверждённый план. `save_plan` всегда снимает утверждение. Повторное утверждение уже утверждённого плана отклоняется.

Каждый успешный task action увеличивает `revision` на 1 и добавляет запись `{revision, action, from_stage, to_stage}` в `history`. Пауза — отдельный флаг, этап не меняется. На паузе доступен только task action `resume`; в done никакие task actions недоступны. Новые сообщения модели блокируются в обоих состояниях. Чтение, память, профили и метаданные чатов сохраняют прежний контракт; это не глобальная заморозка всех ресурсов.

Путь сообщения: owner-lock → проверка replay → запрет paused/done → контекст → DeepSeek → проверка JSON и `kind` → проверка инвариантов → атомарная запись полного хода, метрик, facts, `last_check` и replay. Модель не утверждает план, не сохраняет артефакты и не запускает переходы. Пользователь переносит нужный текст в редактор и явно сохраняет его.

## API задачи

`GET /api/chats/:id` и `GET/PATCH /api/chats/:id/task` возвращают `{chat}`. Поле `chat.task`:

```json
{"stage":"planning","paused":false,"current_step":"","expected_action":"","plan":"","plan_approved":false,"execution_result":"","validation":null,"revision":0,"history":[],"allowed_transitions":[],"transition_reasons":{"planning":"Переход запрещён графом этапов.","execution":"Сохраните и утвердите непустой план.","validation":"Переход запрещён графом этапов.","done":"Переход запрещён графом этапов."}}
```

`allowed_transitions` и `transition_reasons` вычисляются сервером. Причины содержат только запрещённые целевые этапы. `validation` после сохранения имеет вид `{"status":"passed","report":"Проверено"}` либо статус `failed`.

Каждый PATCH содержит `action` и `expected_revision` — целое число ≥0; boolean не принимается. Дополнительные обязательные поля:

| action | Поля | Где доступно |
| --- | --- | --- |
| `update` | `current_step`, `expected_action` | Активный этап |
| `save_plan` | `plan` | planning |
| `approve_plan` | нет | planning, новый сохранённый план |
| `save_execution` | `execution_result` | execution |
| `save_validation` | `status`, `report` | validation |
| `transition` | `target_stage` | По таблице и условиям |
| `pause` | нет | Активный этап |
| `resume` | нет | Только paused |

Пример: `{"action":"save_plan","expected_revision":0,"plan":"Написать CLI и проверить пустой ввод"}`. Поля точные, лишние ключи отклоняются. Шаг/действие — до 500 символов; план, результат и отчёт — непустые строки до 16000 символов. Общий HTTP JSON body — до 32 KiB, поэтому многобайтовый текст может достичь этого лимита раньше. Старые относительные `advance`/`rework` не поддерживаются.

Ошибки: `{"error":{"code":"…","message":"…"}}`. `400 invalid_input` — схема/тип/лимит; `409 stale_revision` — устаревшая ревизия; `409 invalid_transition` — запрет действия или перехода; чужой чат — `404 not_found`; новые сообщения paused/done — `409 task_paused` / `task_done`; неверный ответ модели — `502 provider_error` без нового хода. После 409 интерфейс получает актуальный чат. Task actions не переигрываются автоматически: повтор старой ревизии безопасно отклоняется.

## Контракт модели и сохранённые функции

Ответ без активных инвариантов: `{"kind":"plan","answer":"…"}`. Сопоставление стадий: planning → plan, execution → implementation, validation → validation, done → completion; в done новые запросы не выполняются. Лишние и дублирующиеся JSON-ключи, неверный тип, пустой ответ, обрезанный JSON и неподходящий `kind` отклоняются до записи переписки.

При активных инвариантах дня 14 обязательны также `language`, `architecture`, `budget`: `{"kind":"plan","answer":"…","language":"Python","architecture":"monolith","budget":500}`. Правила проверяются сервером, язык/архитектура — без учёта регистра и без синонимов. Несовместимые типизированные предложения заменяются объяснением отказа, с `last_check.status=blocked`. Профили, три слоя памяти, стратегии контекста, метрики, ветвление и owner isolation сохранены.

Ветви получают префикс переписки, но новую задачу planning, пустые локальные слои, профиль и инварианты; историческое состояние задачи не восстанавливается из checkpoint. Долговременная память общая для владельца.

Повтор завершённого message `request_id` возвращает прежний снимок даже после смены этапа, памяти или паузы. Это не откатывает базу: GET возвращает актуальное состояние. Другой payload с тем же ID — 409. Ошибка провайдера не повторяется автоматически с прежним ID; новый запрос требует новый ID.

## Ограничения

Типизированный `kind` подтверждает форму ответа и её соответствие этапу; он не доказывает смысл свободного текста. Аналогично поля инвариантов не доказывают согласованность всей прозы. Проверка `passed` — явная оценка пользователя, а не самостоятельный запуск тестов приложением.

Сервер рассчитан на один локальный процесс; owner-lock хранится в памяти. Для нескольких процессов нужны общие блокировки запросов, текущая конфигурация этого не обещает. Cookie обеспечивает локальную изоляцию, не полноценный аккаунт. SQLite хранит переписку без шифрования. Токены оцениваются эвристикой UTF-8; стоимость использует историческую таблицу проекта, не текущий счёт провайдера.

В целевом окружении отдельно проверить живой API, доступность выбранной модели/JSON-режима, сетевой timeout и браузерный сценарий. Даже отклонённый ответ может тарифицироваться провайдером. Автотесты с подставными ответами не подтверждают качество живой модели.
