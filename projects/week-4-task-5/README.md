# День 20 — оркестрация нескольких MCP-серверов

Один агент DeepSeek подключается сразу к трём независимым MCP-серверам и сам выбирает подходящие инструменты:

- официальный Airtable MCP — поиск базы и чтение её структуры;
- локальный MusicBrainz MCP — поиск записей в открытом музыкальном каталоге;
- локальный iTunes MCP — поиск треков в каталоге iTunes Store.

Прямые HTTP-запросы к музыкальным каталогам находятся внутри соответствующих MCP-серверов. Агент видит только стандартные MCP tools. Инструменты получают префиксы `airtable_`, `musicbrainz_` и `itunes_`, поэтому маршрутизация однозначна даже при совпадающих исходных именах.

Полная схема Airtable может занимать десятки килобайт. После MCP-вызова оркестратор оставляет для модели только ID и имена таблиц, потому что именно эти данные нужны сценарию. Это снижает расход контекста без подмены результата.

## Что изучаем

- регистрацию нескольких MCP-серверов в одном агенте;
- объединение схем инструментов в общий каталог;
- автоматический выбор сервера и инструмента моделью;
- зависимые вызовы, где результат первого шага содержит ID для следующего;
- передачу результатов разных источников обратно модели для общего вывода;
- ограничение внешнего MCP безопасным read-only allowlist.

## Сценарий

Запрос по умолчанию требует выполнить длинную цепочку:

1. Найти базу `GOOST MUSIC` через Airtable MCP.
2. Передать полученный `baseId` в следующий Airtable tool и получить таблицы базы.
3. Найти `Aerodynamic` группы Daft Punk через MusicBrainz MCP.
4. Найти тот же трек через iTunes MCP.
5. Сравнить сведения трёх источников и сформировать итог.

Порядок вызовов не зашит в Python-код. Его формирует DeepSeek по пользовательскому запросу, описаниям tools и результатам предыдущих шагов.

MusicBrainz ограничивает публичный API примерно одним запросом в секунду. Его MCP-сервер повторяет запрос после временных ответов `429` и `503`, чтобы кратковременная перегрузка не обрывала всю цепочку.

## Установка и запуск

Из корня репозитория:

```powershell
python -m pip install -r projects/week-4-task-5/requirements.txt
python projects/week-4-task-5/main.py
```

Собственный запрос:

```powershell
python projects/week-4-task-5/main.py --prompt "Найди базу GOOST MUSIC в Airtable, затем сравни Around the World группы Daft Punk в MusicBrainz и iTunes"
```

Нужны переменные `DEEPSEEK_API_KEY` и `AIRTABLE_PAT` в окружении или корневом `.env`. Токены нельзя показывать в видео и добавлять в Git.

В агент передаются только два read-only инструмента Airtable:

```text
search_bases
list_tables_for_base
```

Все операции записи Airtable исключены из реестра инструментов и недоступны модели.

## Проверка

Юнит-тесты:

```powershell
Push-Location projects/week-4-task-5
python -m unittest -v
Pop-Location
```

Живой запуск должен показать:

```text
Registered MCP servers:
- airtable: ...
- musicbrainz: ...
- itunes: ...

Round 1: airtable_search_bases(...)
Round 2: airtable_list_tables_for_base(...)
Round ...: musicbrainz_search_recordings(...)
Round ...: itunes_search_tracks(...)
Assistant:
...
```

Порядок независимых запросов к музыкальным каталогам может меняться. Важно, чтобы агент выбрал все нужные серверы, передал настоящий `baseId` во второй Airtable-вызов и построил вывод только по полученным результатам.

## Сценарий видео

1. Показать три MCP-подключения и реестр маршрутов в `main.py`.
2. Показать read-only allowlist Airtable.
3. Запустить `python projects/week-4-task-5/main.py`.
4. Показать регистрацию трёх серверов.
5. Проследить вызовы: Airtable → MusicBrainz → iTunes. Независимые музыкальные вызовы могут поменяться местами.
6. В Airtable обратить внимание на передачу `baseId` из первого инструмента во второй.
7. Показать итоговое сравнение источников.
8. Подвести итог: модель сама выбрала MCP-серверы, инструменты и порядок длинной цепочки.

## Вывод

MCP позволяет агенту одинаково работать с удалённым SaaS и локальными адаптерами. Оркестратор не знает детали API музыкальных каталогов: он регистрирует схемы tools, направляет вызов выбранному MCP-клиенту и возвращает результат модели. Префиксы устраняют конфликт имён, а allowlist не даёт модели получить лишние права Airtable. Такой подход масштабируется добавлением нового MCP-сервера без изменения логики остальных интеграций.
